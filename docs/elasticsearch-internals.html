There is one boundary that explains almost everything in this system: the HTTP request. On your side of it, Node reads bytes, strips wiki markup, and writes JSON. On the other side, Lucene turns text into terms, terms into postings lists, and postings lists into immutable files. Your code never builds an index. It builds documents, and hands them over.

This document follows one corpus — your 20,865 Wikipedia articles — across that boundary and back. Every number in it comes from your actual run.

Part IThe write path

Four stages run in order, but only the last two involve Elasticsearch at all. Stages 1 and 2 are pure text processing: they exist because a MediaWiki dump is not a corpus, it is a backup of an editing system.

01Parse

A 1.05 GB file cannot be loaded into a DOM. WikiXmlParser uses SAX, which emits events — tag opened, text, tag closed — and never holds more than the page currently being assembled. Peak memory stayed at 228 MB against a file five times that size.

The subtlety is that <id> means three different things depending on where it sits: page id, revision id, contributor id. The state machine therefore keys on the path (revision/contributor/id), not the tag name.

No Elasticsearch involvement at all. This stage produces plain JavaScript objects.

02Clean

The <text> element is wikitext, not prose: {{Short description|…}}, {{Sfnm|1a1=Marshall|…}}, [[political philosophy]], infoboxes, tables. Indexing it raw would make sfn one of the most common terms in the corpus and fill every result snippet with braces.

Rendering to plain text is the slow part of the whole pipeline — roughly 100 documents per second, which is where 176 of your 198 seconds went. It also yields the structure for free: categories, section headings, and outgoing links.

77 articles were skipped here. Those render to under 100 characters of prose — template-only pages with nothing to search.

03Create the index

This is the first HTTP contact. PUT /wikipedia_v1 carries the settings and the mapping, and the response comes back before a single document exists.

Your code

Sends a JSON body with settings (1 shard, 0 replicas, 1s refresh) and mappings (21 field definitions, dynamic: strict).

Then issues POST /_aliases to point wikipedia at the new index in one atomic action.

Elasticsearch
  • Writes the index into cluster state and elects a location for its one primary shard.
  • Compiles each field definition into a FieldMapper — the object that will decide, per field, which analyzer runs and which Lucene fields get written.
  • Creates an empty Lucene IndexWriter on disk. Zero segments.

The mapping is the contract. dynamic: strict means a document carrying a field the mapping does not know about is rejected, rather than silently creating a new field with a guessed type. Your load reported failed 0, which is a stronger statement than it looks: all 20,865 documents matched the declared schema exactly.

04Bulk load

The bulk API takes newline-delimited JSON — two lines per document, an action line and a source line:

{"index":{"_index":"wikipedia_v1","_id":"12"}}
{"wiki_id":12,"title":"Anarchism","text":"Anarchism is a political …

{"index":{"_index":"wikipedia_v1","_id":"25"}}
{"wiki_id":25,"title":"Autism","text":"Autism is a neurodevelopmental …

At a 5 MB flush threshold, your 556 MB corpus became roughly 110 of these requests, two in flight at a time. Throughput was 965 documents per second.

Using _id = wiki_id is what makes the whole load idempotent. MediaWiki page ids are stable, so re-running updates documents in place. Note what "update" means to Lucene, though — segments are immutable, so an update is a delete marker on the old document plus a fresh insert. Re-running the same load twice doubles the deleted-document count until a merge reclaims it.

Your code
  • Reads JSONL line by line, never holding more than one document.
  • Accumulates NDJSON to 5 MB, sends, repeats.
  • Sets refresh_interval: -1 first, restores it after.
Elasticsearch, per document
  • Routes it: murmur3(_id) % shards. With one shard, everything lands in the same place.
  • Validates against the mapping.
  • Runs the analyzer on every text field.
  • Adds terms to the in-memory buffer, and appends the raw document to the translog.

Part IIWhat "indexing a field" actually means

This is the core of the entire system, and it is smaller than it sounds. A string goes in; a sorted list of terms and a list of document ids per term come out.

Three things follow directly from this picture.

Analysis is irreversible and happens at write time. Once Anarchism is stored as the term anarchism, the original casing exists only in _source, which is never searched. Changing the analyzer means re-analyzing every document — a full reindex. That is the single constraint that shaped this project's architecture.

Your Phase 1 analyzer is deliberately weak. The standard analyzer tokenizes and lowercases, and that is all. It does not stem, so running and run are unrelated terms. It does not remove stop words, so is, a and and above are all indexed as real terms with real postings lists. That is your baseline, and Phase 3 is where you measure what changes.

Positions cost space. They are stored because match_phrase needs them — asking whether plate occurs immediately before tectonics is a positions query. A field that will never be phrase-searched can drop them with index_options.

Part IIIWhy a document isn't searchable the moment you index it

Searchability and durability are separate properties, achieved by separate mechanisms, at different times. Conflating them is the most common source of confusion about Elasticsearch.

Refresh

Every second by default, Lucene takes whatever is in the in-memory buffer and writes it as a new segment — a self-contained, immutable mini-index. Only then does a new searcher open over it and the documents become findable. This is the "near" in near-real-time.

Your loader sets refresh_interval: -1 for the duration of the load. Without that, 200 seconds of indexing would have produced hundreds of tiny segments, each needing to be merged away, competing with the load for the same disk. With it, you finished with 5 segments.

Flush

A refresh does not guarantee the data is on disk — the new segment may still be in the filesystem cache. A flush performs a Lucene commit, fsyncs, and truncates the translog, because the translog's only job is to replay anything not yet committed. Elasticsearch triggers this automatically.

Merge

Because segments are immutable, deletes are only marks and updates are delete-plus-insert. Merging rewrites several segments into one, physically dropping deleted documents and shrinking the term dictionary. Your 5 segments will consolidate on their own; POST /wikipedia/_forcemerge?max_num_segments=1 does it on demand — useful on a read-only index, wasteful on a live one.

Part IVThe read path

The step worth dwelling on is dis_max. Your multi_match with type: best_fields does not add up the scores from title, redirect, opening_text and text. It computes each independently and takes the maximum.

That choice matters. Summing would let a long article that mentions "tectonics" forty times in the body outrank the article actually titled Plate tectonics. Taking the max means the single strongest signal wins, which for encyclopedic content is almost always the title.

Your avgdl of 1.755

The /explain output you ran returned avgdl: 1.755. That is the title field: across 20,865 articles the average title is under two tokens long.

This is why title^3 is doing more work than the number suggests. A one-token title matching a query term has dl/avgdl ≈ 0.57, which already inflates the score through length normalisation — before the 3× boost multiplies it again. Length normalisation and your boost compound.

It also means the boost is hard to reason about by eye, which is the argument for a judgment set: title^3 is currently a guess, not a measurement.

Statistics are per shard

N and n are counted within a shard, not across the index. With your single shard they are exact corpus-wide figures. Split into five shards and each computes IDF from its own fifth, so the same document can score differently depending on where it landed — the classic surprise when a small index is over-sharded. One shard for 20,865 documents is the right call, and it makes your scores reproducible.

Part VIWhat's actually on disk

Inside the container, a segment is a group of files sharing a name prefix. Each holds one of the structures above:

FileHoldsRead when
.tipTerm index — an FST mapping term prefixes to offsets in the dictionary, held in memoryevery term lookup
.timTerm dictionary — the sorted terms themselvesevery term lookup
.docPostings — document ids per term, delta-encodedmatching
.posTerm positions within each documentmatch_phrase only
.fdt / .fdxStored fields — your _source, LZ4-compressedfetch phase, top 10 only
.dvd / .dvmDoc values — columnar, per-fieldsorting, aggregations
.livLive-docs bitset — which documents are not deletedevery query

This explains a number that surprised both of us: 556 MB of JSONL became a 356 MB index. The _source is stored LZ4-compressed, and the inverted index stores each distinct term once rather than every occurrence of it. The searchable structure genuinely costs less than the text it was built from.

Doc values, and why title.keyword exists

The inverted index answers "which documents contain this term?" It cannot answer "what is the title of document 12?" without scanning — wrong direction. Sorting and aggregating need the column, so Lucene writes a second, columnar copy: doc values.

text fields have no doc values, which is why your mapping declares title.keyword and categories.keyword. Those subfields are the ones that will make Phase 5's category aggregation possible. It is the same source string written to disk twice, in two shapes, for two questions.

Where the FST turns up

A finite state transducer stores a large set of strings in very little memory by sharing prefixes and suffixes, while still mapping each to a value. Lucene uses one for the term index so that locating a term never requires a linear scan of the dictionary. The same structure powers completion suggesters — which is the machinery your Phase 2 autocomplete will sit on.

Part VIIILoose ends in the current index

Three things in your mapping are not yet doing what their comments claim. Better to know now than to discover them while debugging relevance.

title.exact is currently identical to title

The subfield declares analyzer: "standard", and the parent title — having no analyzer specified — also defaults to standard. Both fields therefore produce exactly the same terms, and you are paying to index the same strings twice.

It becomes meaningful the moment Phase 3 gives title a stemming analyzer while .exact stays standard. Until then it is dead weight, and worth deleting if you want a clean baseline.

Stop words are being indexed

The standard analyzer ships with an empty stop-word list. Every the, is and of across 20,865 articles has a full postings list. That is intentional for Phase 1 — it is the baseline you will measure against — but it is a real share of your 356 MB.

outgoing_links is indexed but unqueried

Up to 1,000 keyword values per document, and nothing in your API touches them yet. They are there for link analysis later; if the index size ever becomes a problem, this is the first field to reconsider.

What changes in Phase 3

Everything in Part II is fixed at write time, which is why the analyzer work needs a reindex rather than a settings change. The sequence is: define wikipedia_v2 with the new analyzer, replay data/wikipedia.jsonl into it, then move the alias. Your API queries wikipedia, so it picks up the swap without a restart.

That is the payoff for the JSONL cache and the alias indirection — two decisions made in Phase 1 that only start earning their keep now.
